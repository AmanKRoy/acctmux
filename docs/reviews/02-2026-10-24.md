### 2. Architecture

- Lazy children, one process per credential set, one HTTP daemon: still the right design for upstreams that bind credentials at startup. Benchmark: 402 MB at 8x2 vs 2481 MB for plain stdio; about 100 MB PSS per active account; 2.2 s cold start.
- Challenge: a single tool surface removes client-side per-account permissions (Claude Code and OpenCode permission rules match tool names, not arguments). MCPlexer sells exactly this. Alternative: hybrid `expose: "selector" | "prefixed" | {prefixed: [tools]}` (for example `work__send_email` per account, the rest shared).
- Stateless by default buys little (about 2 ms per request) and loses explicit cancel, `listChanged` and future progress forwarding. Recommend stateful as default after a real Claude Code session check, stateless as fallback.
- stdio-only upstreams is the biggest limit on generality (Google official, Notion remote and most SaaS servers are remote/OAuth). Remote upstreams with a per-account token store would make this a layer for any MCP server.
- Docs vs design: ARCHITECTURE "Known limits" contradicted the code (resources/prompts, cancellation, startup child); Goal still said "N Google accounts".

What acctmux combines that none of the inspected projects do: a generic selector-injected single tool surface over arbitrary stdio servers; lazy per-account children shared by N sessions with idle kill; server-side per-account policy; quota-failover pools with half-open recovery and usage-aware ordering (the most novel part). Others do better: remote upstreams and OAuth, client-side per-account permissions, isolation, raw memory for Google (taylor).
