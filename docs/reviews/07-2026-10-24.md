## Report

I'd publish it on GitHub now, and publish to npm only after two things change. First, the first-run experience: right now it is the author's own Google setup and fails with no useful message. Second, the docs: they claim more than the code delivers. The code is in good shape and the benchmark reproduces. What's weak is onboarding, how the project is positioned, and parts of what ships in the package.

Everything was read-only on the repo. I worked in a scratch copy with a fake HOME and the repo's fake upstream, on ports 18723-18726. Live :18704, systemd, `~/.config` and credentials were not touched. All my processes are killed and the ports are free. Some processes on :18720 under `scratchpad/head/` belong to another agent (probably review 06), so I left them alone.

**Baseline:** lint is clean and CI is green (last 3 runs). I couldn't run the full 118-test suite inside the 10 allowed ports: the suite keeps every router it starts alive until the end of the run (about 100 processes). The first 19 tests passed before it ran out of ports. The packed tarball installs (25 files, 68 kB packed, 196 kB unpacked; 96 dependencies, 27 MB, MCP SDK 1.32.2). `--version`, `--help`, `tools/list` and a `tools/call` on account b all work from the installed tarball.

## Efficiency compared with the alternatives

PSS, aggregated over the process tree:

| Setup | 1 session × 1 account | 8 sessions × 2 accounts | Idle after the run |
|---|---:|---:|---:|
| acctmux, Google (report) | 199 MB | 402 MB (3 processes) | about 45 MB (router alone, my measurement once workers are stopped) |
| stdio per session (report) | 156 MB | 2481 MB (16) | 0 (no daemon) |
| punkpeye mcp-proxy, one per account (report) | 246 MB | 584 MB (4) | 446 MB (stays resident) |
| supergateway stateful (report) | 248 MB | 2713 MB (18) | 175 MB |
| taylorwilsdon workspace-mcp HTTP, direct (report) | 122 MB | 139 MB (1) | 113 MB |
| acctmux + fake upstream, HEAD (my run, 1 rep) | 67 MB | 157 MB | 45 MB |

Latency, warm call (my run at HEAD vs report): acctmux 1.1 ms (N=1) and 3.4 ms (N=8) against the report's 2.0 / 6.1 ms. mcp-proxy was 1.1 / 3.3, supergateway 0.9 / 2.7, stdio 0.0 / 0.3. The report's claims hold at HEAD and are on the conservative side.

Tool-definition size per session: 58 KB vs 104 KB.

The "when not to use it" section is honest and matches the data. The "Idle after the run" column is the strongest efficiency argument and the README never mentions it: about 45 MB at rest, against 446 MB for mcp-proxy per account and 113 MB for taylorwilsdon. That idle row combines my measurement (router alone, after its workers were stopped) with the report's snapshots, so it's derived, not measured in one run.

## Is it needed, and what a Hacker News reader would attack

- **Need:** real but narrow. It fits people with 2 or more accounts of a stdio server that binds credentials at startup, used from several client sessions. Upstreams are moving to remote servers with OAuth (Google's official servers, still Developer Preview; Notion; GitHub remote). acctmux is stdio-only, so its audience is shrinking.
- **What's unique (unchanged):** a selector argument on any stdio server, lazy per-account workers shared by all sessions, per-account policy, and pools. AWS's `mcp-proxy-for-aws` (`aws_profile`) confirms the selector pattern, for AWS only.
- **Likely attacks:**
  1. Omitting `account` silently uses the default account, even for `send_email` (C13). This is the strongest safety criticism of a multi-account tool.
  2. "Independent review" turns out to be Claude reviewing Claude.
  3. "Saves about 180 MB versus mcp-proxy" isn't a reason to run a daemon.
  4. The default upstream is a stale 37-star package at the author's own path.
  5. It's built on the older protocol and SDK.
  6. The one-file design.

## Verdict

- **Publish on GitHub:** yes. Flipping the repo to public is your call, and it also fixes every 404 link. Fix 4 and 6 first (relabel or move the review docs, update the stale facts); both are quick.
- **Publish to npm:** not yet. Do 1, 2, 4 and 7 first, then 8 — roughly half a day.
- **Would I star it:** yes, as a well-evidenced niche tool, once the README leads with the selector, policy, pools and the idle footprint.
- **Biggest blocker:** the npm first run. A stranger who runs `npx acctmux` gets two cryptic lines and exit 1, because the no-config default is the author's own Google install. The README's quick start doesn't help: it's a copy-from-a-git-checkout flow for that same setup. Fix 1 and 2 together.
