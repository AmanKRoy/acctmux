## 2. Architecture

No change. Every startup finding since review 03 comes from loading every upstream fully before listening. N3 is still about 2x the budget: about 90 s worst case at defaults, while systemd sees "running" and clients get connection refused. Listening first and loading in the background is still the structural fix (size M). Nothing in this round argues against the design itself.

## 3. Differentiation (rechecked 2026-10-24)

**taylorwilsdon.** Issue #926 is still open. PRs #928 and #1049 are open and not merged. **v2.2.0 was released 2026-10-23 22:26 UTC.** Its release notes do not touch multi-account or rebind, so the README:158 argument stands. But README:19 and README:158 still say "v2.1.2 is the latest".

**antoniofulg/mcp-account-router.** 0 stars, no push since 2026-10-11.

**New and not cited: `mohanagy/miftah`** (`@lubab/miftah` 1.1.6, MIT, 5 stars, claims 1.0 stable).
- What it does: "one connector, named profiles" in front of an existing MCP server, with policy, approvals, redaction, audit metadata, an OS-vault, OAuth for remote HTTPS upstreams, a wizard and a browser Console.
- What it does better than acctmux: setup UX, credential handling, remote/OAuth upstreams, maturity.
- What it does not do: switching is stateful (`miftah_use_profile` sets the active profile for that Miftah process), not a per-call selector. Nothing I read in its README describes a daemon shared across client sessions, lazy idle-killed workers per account, or pools.
- It is the closest prior art found so far, and README "Related projects" should name it.

**Still unique to acctmux:**
- A per-call selector, so one session can use two accounts at the same time.
- One shared daemon for all sessions, with lazy per-account workers.
- Per-account policy.
- Quota pools.
