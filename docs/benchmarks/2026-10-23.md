# Benchmarks, 2026-10-23

> acctmux was called gw-mcp-router when this was measured; the name below is historical. Links to scripts and raw JSON point at the repository because those files are not part of the npm package.

gw-mcp-router against the ways people usually serve several Google accounts to several MCP client sessions. Harness: [`scripts/bench.mjs`](https://github.com/AmanKRoy/acctmux/blob/main/scripts/bench.mjs). Raw, secret-free results: [`2026-10-23-google.json`](https://github.com/AmanKRoy/acctmux/blob/main/docs/benchmarks/2026-10-23-google.json), [`2026-10-23-fake.json`](https://github.com/AmanKRoy/acctmux/blob/main/docs/benchmarks/2026-10-23-fake.json), [`2026-10-23-google-expired-tokens.json`](https://github.com/AmanKRoy/acctmux/blob/main/docs/benchmarks/2026-10-23-google-expired-tokens.json). Every table below can be regenerated with `node scripts/bench.mjs summarize <file>`.

## Findings

All numbers are medians unless stated; n is the number of samples behind them. N = concurrent client sessions, M = Google accounts (`default`, `ai`).

1. **Memory scales with sessions for stdio and supergateway, not for the router.** Aggregate PSS of the whole process tree at N=8, M=2: stock stdio 2481 MB (16 processes), supergateway stateful 2713 MB (18), mcp-proxy per account 584 MB (4), **gw-mcp-router 402 MB (3)**. Across 3 reps the spread is under 3 % for all four.
2. **The router costs more than stdio for one session.** N=1, M=1: stdio 156 MB, router 199 MB. The router process itself is 43 MB PSS idle and grew to 66-73 MB with 8 busy sessions (118 MB in the Google-free suite at N=8, M=2).
3. **taylorwilsdon's workspace-mcp over HTTP is the cheapest setup measured**: one Python process for all sessions and accounts, 139 MB at N=8, M=2 when started from its installed entrypoint (230 MB via `uvx`, see 8). For Google accounts specifically it beats the router on memory by about 3x.
4. **But its native multi-account mode fails calls.** When the second account in a session needs an access-token refresh, workspace-mcp refuses with `SECURITY: Attempt to rebind session ... to <other account>` and answers with a login request. Reproduced with expired access tokens: stdio failed in every session of every repetition (3/42 and 6/84 calls), HTTP in every N=1 repetition and 2 of 3 N=2 repetitions (3/42, 2/84); every failure was the second account's first call. The same workspace-mcp behind the router (one process per account) had 0/126 failures under the same conditions. In the main matrix, where tokens were mostly fresh, 2 of 23,670 calls failed, both workspace-mcp stdio: one was this error, the other a Google HTTP 503 `Backend Error`.
5. **Warm tool-call latency is Google's, not the framework's.** list_calendars/list_labels: router 399 ms, stdio 388, mcp-proxy 399, supergateway 395, workspace-mcp HTTP 416-419 (n=1350 each, p95 519-560, interquartile ranges overlap). Exception: supergateway stateless, 2119 ms, because it starts a new server for every request.
6. **Framework overhead without Google** (fake upstream, `echo`, n=450 per config at N=1, n=3600 at N=8): stdio 0.09 ms, supergateway 1.8 ms, router 2.0 ms, mcp-proxy 2.3 ms; with 8 sessions calling back to back: stdio 0.24, supergateway 4.9, mcp-proxy 5.8, router 6.1 ms. That is the price of the HTTP hop and a single Node process, about 1-1.5 % of a Google call.
7. **Session start**: router 6 ms (35 ms p95, the first connection), mcp-proxy 8 ms, workspace-mcp HTTP 7 ms, against about 1.07 s for every stdio session (spawn 3.5 ms + initialize 1.06 s), 1.09 s for supergateway stateful (it spawns a server per session) and 2.2-2.3 s for workspace-mcp stdio. **Cold account in the router**: the first call to an account without a running worker took about 2.2 s (spawn, initialize, the `get_storage_quota` warm-up and the call); the default account's worker is started with the router, so its first call took 0.45-0.53 s.
8. **`uvx` keeps a resident wrapper.** The `uv` process stays alive as the parent of the Python server and held 20-158 MB PSS (mostly anonymous memory, varying between runs). Running the cached environment's `workspace-mcp` entrypoint directly removes it; the "-direct" rows show that.
9. **No account mix-ups.** All 8,908 successful list_calendars results in the main matrix named the requested account's address and no other.

## Method

**Client.** One hand-written JSON-RPC client for all configurations (newline-delimited stdio, or HTTP POST with JSON or SSE responses and `mcp-session-id` handling), protocol version 2025-06-18. No MCP SDK on the client side, so client cost is the same everywhere.

**Matrix.** N in {1, 2, 4, 8} x M in {1, 2} for 11 Google configurations, 3 repetitions each (264 cells); 5 configurations x the same N, M x 5 repetitions for the fake suite (200 cells). Repetitions are the outer loop, so drift over time spreads across all configurations.

**One cell, step by step, with the timing boundaries:**
1. *Daemon ready*: from the `spawn()` call until the port accepts a TCP connection (router, mcp-proxy, supergateway, workspace-mcp HTTP). The router only listens after it has started the default account's worker, run the warm-up and cached the tool list, so its daemon time includes that work. Then 1 s settle and an idle memory snapshot.
2. *Session ready*, sessions opened one after another: from the start of the session until every endpoint of that session has answered `initialize`. A session has one endpoint per account for stdio, mcp-proxy and supergateway, and one endpoint for the router and workspace-mcp; endpoints of a session start in parallel. For stdio endpoints *spawn* (from `spawn()` to the process `spawn` event) is recorded separately from *initialize* (request sent to response received, which includes the server's own startup). Then `notifications/initialized` and the first `tools/list`, whose tool count and JSON size are recorded.
3. *Workload*: all N sessions at once, calls sequential within a session, no pause between calls. Per account: the **first call** (`list_calendars`; the cold boundary is "first `tools/call` for this account in this session"), one `list_labels` warm-up (excluded), then 5 rounds of both tools (**warm**), then 5 `tools/list` calls (Google-free). For stdio and the proxies the first call is also the first Google request of a freshly started server. For the router the default account's worker is already warm from startup, and the second account's worker is started by the first call; because the workload starts in all sessions at the same moment, all N sessions wait for that one spawn, which is why the router's `ai` first call is about 2.2 s in every session, not only the first.
4. *Memory snapshot* after the workload, with all sessions still open, 0.5 s settle.
5. Sessions closed (stdin end or HTTP DELETE), then every process group the harness created is terminated (SIGTERM, then SIGKILL after 4 s).

**Workload per family.** google-workspace-mcp: `list_calendars`, `list_labels`. workspace-mcp: `list_calendars`, `list_gmail_labels`, plus `user_google_email` in native mode or `account` behind the router. Both hit the same Google endpoints (Calendar calendarList, Gmail labels), but the server code and result formatting differ. All calls are read-only. Fake suite: `echo` on `tests/fake-upstream.mjs`.

**Memory.** The tree is every process the harness spawned plus all their descendants, found by walking parent PIDs over `/proc/*/stat` at snapshot time. The harness (client side) is excluded. For each process `/proc/<pid>/smaps_rollup` gives Rss, Pss and Private_Clean + Private_Dirty (USS); the tables sum them over the tree. PSS splits each shared page between every process that maps it, including processes outside the tree (the live router, other Node processes), so the PSS sum is the tree's share of memory, not an exact marginal cost; USS, the memory only these processes use, is a lower bound for what stopping the tree frees and was 0-17 % below PSS here (raw JSON has both). The snapshot is one point after the workload, not a peak and not a long-run steady state. Short-lived processes (supergateway stateless starts one server per request) are not in the snapshot.

**Account identity.** Every successful `list_calendars` result is checked to contain the requested account's address and not the other account's; results store only the verdict (`match`, `mixup`, `both`, `none`).

**Statistics.** Medians; p95 only where n >= 20; interquartile range, min and max in the raw summary. Failures are counted per call (JSON-RPC error, timeout, or `isError` result) and kept with their scrubbed message.

**Credentials.** google-workspace-mcp configurations use the real token files under `~/.config/google-workspace-mcp` (the files the live router uses). workspace-mcp configurations use copies converted by `scripts/dguido-to-taylor.mjs` into the benchmark's scratch directory, deleted after the run. Results contain account labels only; e-mail addresses and URL query strings are scrubbed from error texts.

## What this means

- **Use the router** when several client sessions need several accounts of a stdio-only, one-account-per-process server such as google-workspace-mcp: at 8 sessions x 2 accounts it used 16 % of the stdio PSS and 69 % of mcp-proxy's, gives each session one 54-tool list instead of 108, starts a session in milliseconds, and adds 2-6 ms to calls that take 400 ms anyway.
- **Do not use it** for a single session with a single account (stdio is 43 MB smaller and has no daemon), or when a natively multi-account server is reliable for your accounts: workspace-mcp over HTTP used about a third of the router's memory (139 vs 402 MB at 8x2). The router's advantage over workspace-mcp here is isolation (one process per account, so no session rebinding failures and no cross-account state by construction) and per-account tool policy; its cost for two accounts was 236-263 MB more with google-workspace-mcp workers and 138-178 MB more with workspace-mcp workers.
- mcp-proxy is the closest alternative for google-workspace-mcp: flat in N, but one proxy plus one server per account kept resident (88-138 MB per proxy) and M tool lists per session. supergateway stateful grows like stdio because it starts a server per session.

## Limitations

- One machine, one home network, one day. Google latency varies by minute; only 3 repetitions for the Google suite. The warm-call medians of all non-stateless configurations differ by less than their interquartile ranges, so no ranking among them is claimed.
- Sessions call without pauses. Real clients are idle most of the time, which favours the lazy designs less in latency and more in memory.
- Memory is one snapshot after the workload. The router's heap growth under concurrent load (finding 2) was not followed over time; whether the garbage collector returns it was not measured.
- PSS depends on what else maps the same files (see Method). The "-direct" and `uvx` variants differ only in the wrapper; the `uv` process size varied between 20 and 158 MB without an identified cause.
- workspace-mcp was run in its legacy multi-user and single-user modes; its OAuth 2.1 multi-user HTTP mode was not tested. The expired-token failure was reproduced by forcing expiry on copied credentials; in the main matrix it appeared twice on its own.
- mcp-proxy's earlier-observed rejection of google-workspace-mcp's `get_status` result (see docs/ARCHITECTURE.md) was not re-tested; `get_status` is not in this workload.
- google-workspace-mcp configurations used the same token files as the live router; nothing in this run triggered a refresh failure.

## Reproduce

Prerequisites: Linux (`/proc/<pid>/smaps_rollup`), Node 20+, npm, `uv`/`uvx` for workspace-mcp, google-workspace-mcp installed at `~/.local/share/mcp-servers/google-workspace` with at least one authenticated profile. No TTY needed.

```bash
WORK=$(mktemp -d)                                   # scratch dir, owned by the benchmark
node scripts/bench.mjs setup --work-dir $WORK       # mcp-proxy and supergateway into $WORK/tools
node scripts/bench.mjs run --work-dir $WORK --suite fake --reps 5 --out fake.json          # no account needed

cp scripts/bench/accounts.example.json $WORK/accounts.json   # fill in labels, profiles, addresses (stays local)
node scripts/bench.mjs setup --work-dir $WORK --accounts-file $WORK/accounts.json  # + workspace-mcp creds, uv cache
node scripts/bench.mjs run --work-dir $WORK --suite google --accounts-file $WORK/accounts.json --reps 3 --out google.json
node scripts/bench.mjs run --work-dir $WORK --suite google --accounts-file $WORK/accounts.json --taylor-reset \
  --configs taylor-stdio-direct,taylor-http-direct,router-taylor-direct,router --sessions 1,2 --accounts 2 --reps 3 --warm 2 --out expired.json
node scripts/bench.mjs summarize google.json
rm -rf $WORK                                        # removes the converted workspace-mcp credentials
```

Ports 18720-18919 on loopback are used (rotated per cell, because workspace-mcp refuses to start on a port still in TIME_WAIT). The full Google suite takes about 80 minutes and makes about 17,800 read-only tool calls that reach Google (plus about 5,900 `tools/list` calls that do not).
