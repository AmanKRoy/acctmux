# Benchmark: four real Google accounts (2026-10-26)

Scaling run of the 2026-10-23 matrix. Same harness (`scripts/bench.mjs`), same upstream, now with four real accounts instead of two. Raw data: [2026-10-26-google-m4.json](2026-10-26-google-m4.json).

## Results

Eight sessions, four accounts each (32 account connections), read-only `list_calendars` and `list_labels` calls.

| Setup (google-workspace-mcp unless noted) | PSS, 1 session × 4 accounts | PSS, 8 sessions × 4 accounts | Session start (8 sessions) | Warm call | Tools per session |
|---|---:|---:|---:|---:|---:|
| **acctmux** | 698 MB (5 processes) | **778 MB (5)** | 2.3 ms | 386 ms | **54** |
| Stock stdio, one server per session per account | 628 MB (4) | 4938 MB (32) | 767 ms | 388 ms | 216 |
| supergateway, stateful, one per account | 995 MB (8) | 5371 MB (36) | 789 ms | 387 ms | 216 |
| mcp-proxy, one per account | 989 MB (8) | 1166 MB (8) | 5.4 ms | 387 ms | 216 |
| taylorwilsdon workspace-mcp, HTTP, native multi-account | 124 MB (1) | 140 MB (1) | 3.0 ms | 395 ms | 38 |
| workspace-mcp behind acctmux | 470 MB (5) | 562 MB (5) | 2.3 ms | 389 ms | 38 |

## Findings

- **Memory vs stdio:** at 8 sessions × 4 accounts acctmux uses 778 MB against 4938 MB (6.3 times less), 5 processes against 32.
- **Memory vs mcp-proxy:** 778 MB against 1166 MB (33 % less). Both run one process per account; acctmux shares them across sessions and does not wrap each in a second process.
- **Tool definitions:** 54 per session against 216. The upstream's tool list is repeated per account everywhere except acctmux.
- **Session start:** 2.3 ms against 767 ms for stdio and supergateway (which spawn servers per session).
- **Warm calls:** 385-395 ms for every setup. That is Google's latency, not the framework's.
- **Cold account:** the first call to an account without a worker took 1.7-1.9 s in acctmux (0.4-0.9 s elsewhere). The default account's worker starts with the router.
- **Where acctmux is not smallest:** at one session, stdio uses less (628 vs 698 MB). taylorwilsdon's `workspace-mcp` in native multi-account mode uses far less memory (140 MB) in this run; its multi-account failure mode is described in the 2026-10-23 report.
- **Reliability:** 0 failed calls out of 6,534 in all 12 cells (6 configs × 1 and 8 sessions, 2 repetitions); every account answered with its own data.

## Method and limits

- Same machine as 2026-10-23 (Intel Core Ultra 9 185H, 31.5 GB, Omarchy, kernel 7.2.8-9), same pinned versions: @dguido/google-workspace-mcp 3.4.4, mcp-proxy 6.7.21, supergateway 4.2.0, workspace-mcp 2.1.2.
- Router: `router.mjs` and `lib/` unchanged since commit a74c414 (benchmarked at d67fa4f).
- Four real consumer accounts, logged in; the live acctmux service and a desktop session were running during the run. Cells ran one at a time.
- PSS is summed over the process tree (`/proc/<pid>/smaps_rollup`). Two repetitions per cell (the 2026-10-23 run used three), medians reported. Spread between repetitions was under 2 % for every PSS cell.
- Memory here is higher per account than the credential-free numbers in 2026-10-25.md, because the workers are logged in and make real Google calls.
- Tool-definition counts for stdio, supergateway and mcp-proxy are measured (216 for four accounts), not extrapolated.
- Single machine, single day. Read the 2026-10-23 report's limitations before generalising.

## Reproduce

Same as the 2026-10-23 report, with four accounts in the accounts file (labels must equal the profile names) and:

```bash
node scripts/bench.mjs run --work-dir $WORK --suite google --accounts-file $WORK/accounts.json \
  --configs taylor-http-direct,router-taylor-direct,router,mcp-proxy,supergateway,stdio \
  --sessions 1,8 --accounts 4 --reps 2 --out google-m4.json
```
